# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Header-only C++ library of speed-optimized DSP building blocks using x86 SIMD intrinsics. Everything lives in `include/`; there is no build system, library target, or CI. Active development is almost entirely in `include/evm.h` (efficient vector math), `include/evm_trig.h` (the SIMD sine, cosine and atan2 its polar/cartesian conversions use) and their tests. Other headers will be updated
or added over time but may not work right now.

## Building and testing

Tests are compiled by hand from inside `unit_test/` (each `.cc` has its compile line in its header comment). C++17 is required by `evm.h`.

```sh
cd unit_test
g++ -std=c++17 -march=native -O3 -I../include/ -o evm_unit_test evm_unit_test.cc
./evm_unit_test            # random seed, printed at start
./evm_unit_test 12345      # reproduce a run with a specific seed
```

Exit status is 0 only if every check passes. There is no per-test filter: the binary always runs the full suite (about 100 checks, a few seconds).

The SIMD branches are independent implementations, so test each one by forcing dispatch down with macros:

```sh
g++ ... -DDISABLE_AVX512 ...   # AVX2/AVX branch
g++ ... -DDISABLE_AVX2 ...     # AVX branch
g++ ... -DDISABLE_SIMD ...     # scalar "default" branch
g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -I../include/ -o ut_san evm_unit_test.cc
```

The untracked `ut_AVX`, `ut_AVX2`, `ut_scalar`, `ut_san` binaries in `unit_test/` are these variants. The code also targets Intel `icpx` (`-xHost` in place of `-march=native`). `evm_tail_speed_comparison.cc` is a benchmark, not a test. There is no `.gitignore`, so never stage built binaries.

Build and test with both g++ and icpx, make sure to test AVX512, AVX2, AVX, and
default paths through use of DISABLE_<ISA>. With icpx, also build with `-DDISABLE_SVML`, which switches the polar/cartesian functions from SVML to `evm_trig.h`.

## evm.h architecture

**Runtime dispatch via function multiversioning.** Each public function is defined several times with the same signature, each with `__attribute__((__target__("avx512f")))`, `"avx"` (sometimes `"avx2"` / `"avx2,fma"`), and `"default"`. GCC/icpx pick the best variant at runtime from the CPU, regardless of `-march`. Every non-default variant is wrapped in `#if !defined(DISABLE_<ISA>)`. SSE variants exist only for `getOptLevelRaw()`. Adding a function means writing the AVX512, AVX, and default variants, each with its guard.

A plain (non-multiversioned) wrapper that calls a multiversioned function, such as the by-value `dotp`/`dotpc` wrappers, `magSq(float)` and `abs`, must be defined after every target version of that function. Declare it in the top half, define it after the `default` version. Defined earlier, icpx refuses to compile the header, and g++ binds the call to the first clone (`.avx512f`), so there is no runtime dispatch.

**File layout.** The top half of the file has doc-commented declarations grouped by `//===// Section //===//` banners. The bottom half has matching `// <Section> Function Implementation //` banners with the definitions. Keep the two in sync. The file-header comment lists the operations and their accuracy and speed tradeoffs. The specialized functions (tune, fs2Shift) are listed there but not implemented yet.

**Tail handling is where bugs live.** Main loops process full registers. The final partial register uses masked loads and stores: `masks[rem]` with `_mm256_maskload_ps`/`maskstore` for AVX, and `mask16(rem)` with `maskz_loadu`/`mask_storeu` for AVX512. Complex data uses `masks[rem<<1]`. Every function must:
- treat `len <= 0` as a no-op,
- never write past `out[len-1]`,
- work in place (`out` may alias an input).

`evm_unit_test.cc` sweeps every remainder for 4/8/16-element registers, plus negative lengths, to catch these bugs. Register new functions there via `check<>()` with the right tolerance class: `TOL_EXACT` for true multiply/divide, `TOL_NR` for reciprocal plus one Newton-Raphson step, `TOL_RCP` for a bare reciprocal, `TOL_CMP` (exact) for comparison and selection. The doubles baseline is computed with `std::complex<double>`. The dot-products are reductions and go through `checkDot()` instead; they must set the result to 0 when `len <= 0`. `dotpRev` and `dotpcRev` pass it `revB`, which pairs `a[k]` with `b[len-1-k]`; in2 starts right after a NaN element, so a read before its start shows up too. The normalized dot-products (`dotpn`, `dotpnr`, `dotpcn`, `dotpcnr`) go through `checkDotN()`, which sums p/|p| in double, skipping each product whose squared magnitude is below FLT_MIN, and measures the error against the number of terms. Each also runs with in1 = `gZc`, whose zero products must add nothing. Output buffers are pre-filled with a NaN sentinel that is matched by its bit pattern, so a NaN computed by a kernel counts as a wrong value or a stray write, not as an untouched element. The complex magnitudes run on `gZc`, which has a zero in every third element, because `x*rsqrt(x)` is `0*inf = NaN` at zero unless the kernel guards it. Its zeros cycle through all four sign combinations, because `atan2(±0, -0)` is ±π (`cartToPol` runs on it too). `nmag`/`nmagr`/`nmagnr` and the magnitude sums and biases (`magSum`, `magrSum`, `magSqSum`, `magBias`, `magrBias`) run on it as well; a zero must normalize to 0. The three sums add to the output buffer, so their tests pass the values it starts with as in2 (the lambda copies them in) and pass `check<>()` `overComplex = false`, which leaves out the mode that puts a real output on top of the complex input. They, the biases and `magSqDiff` also pass a magnitude function, since their results can cancel. `magSqDiff` runs a second time with its inputs swapped, so that mode also covers out on top of in2. `magSq`, `mag`, `magr`, the biases, the sums and the normalizations also go through `checkMagSpecial()`, which runs zeros of all four signs, values whose squared magnitude underflows, is a denormal or overflows, infinities, NaN and denormal parts through every lane at lengths 1 to 40. NaN, INF and exact zeros must match (an overflowing |in|^2 gives INF; the normalizations give each part a zero of its own sign, or NaN where it is NaN or INF, wherever |in|^2 is below FLT_MIN, INF or NaN). A denormal |in|^2 may give a magnitude of 0, and `magr` on the AVX-512 path may give NaN for an overflowing |in|^2 (see below). With icpx, the normalizations are only checked there on the SIMD paths, for the same fast-math reason as the inverse square roots. The comparison functions run on `gNf`, whose values are a multiple of 0.5 half of the time, so ties with the threshold and equal magnitudes of opposite sign are common. `minMax` with two output buffers goes through `checkPair()`, which also runs each output on top of either input, and the `minMax` reduction goes through `checkMinMax()`, which puts a single min or max at every position. Where a stray write could put back the sentinel unchanged (min/max of two sentinels, `zneg`/`zpos` in place), those tests fill the area past the end with values the kernel would change. `multSum` and `multcSum` also pass `check<>()` a magnitude function, |in1*in2|+|in3|, to measure the error against, because their results can cancel to near zero; their "a=in3" runs pass in3 as the a buffer so the in-place modes also cover out on top of in3. `multe`, `dive`, `divre` and `divnre` go through `checkExpand()`, which requires every imaginary part to be left exactly as it was (the sentinel, or in place the input float under it) and runs with the complex output over in1 or in2. The divide-gather functions (`divg`, `divrg`, `divnrg`) go through `checkGather()`, which runs strides from 1 to INT_MAX on the 16K-element `gGa`/`gGb`, each output count with the shortest and the longest input that gives it, and requires everything past `out[n-1]` to be left as it was (in place, the rest of the input); `len <= 0` or `stride <= 0` must be a no-op. On unix-like systems it also runs each case with the inputs ending right before a `PROT_NONE` page and catches the SIGSEGV. The small strides load whole registers, so a read past the end would otherwise go unseen. Their eps overloads, `divSqrt`'s and the inversion functions' (`inv`, `invr`, `invnr`, `invs`, `invrs`, `invnrs` and their `Sqrt` forms, run on the divisors `gBf`) use `GEPS` = 0.5, which raises every negative divisor, and `divSqrt` and the inverse square roots without eps run on `gPf` = |`gBf`|. The inversion functions also go through `checkInvSpecial()`, which runs zeros of both signs, infinities, NaN and the largest and smallest normal floats through every lane at lengths 1 to 40, with and without eps, and the scaled ones with a scale of -0 too. NaN, infinities and signed zeros must match exactly, and a result below FLT_MIN may come out as a zero of the same sign. Denormal inputs are included for the true versions, and for the approximations only under DAZ, since without it AVX/AVX2 `rcp_ps`/`rsqrt_ps` treat them as zero. With icpx, the inverse square roots are only checked there on the SIMD paths: its fast math turns `1.0f/sqrtf` in the default versions into `rsqrt` and a Newton-Raphson step, which gives NaN at 0 and INF. The integer to float conversions run on `gI8`/`gI16`/`gI32` and must equal `static_cast<float>` exactly; their "in place" runs go through the `void*` wrappers, whose float output is wider than the integer input, and the min/max overloads go through `checkCnvrtMinMax()`. `polToCart` always uses `evm_trig.h`; the other polar/cartesian SIMD versions use SVML when `EVM_SVML` is defined (icpx without `-DDISABLE_SVML`) and `evm_trig.h` otherwise. Their error is measured against `TOL_TRIG`. The polar ones also run on large phases (`gLc` up to 1e4 cycles, `gLr` up to 1e7 radians, far past the 65536 where `evm_trig.h` hands lanes over to scalar `sincosf`), and `checkPolarSpecial()` runs grids of zeros of both signs, ±1, infinities, NaN, denormals and the largest floats through all four, requiring NaN and infinities exactly and the sign of a zero angle. icpx turns on FTZ/DAZ by default, so there denormal inputs act as zeros (the double references see them that way too) and denormal results may come out as 0; `check<>()` accepts a 0 for a result below FLT_MIN only while flush to zero is on (it reads MXCSR), so g++ builds still check denormal results.

**Deliberate choices that look like bugs:**
- Division kernels divide the zero-filled unused lanes of the last register (0/0), which raises `FE_INVALID`/`FE_DIVBYZERO` on valid input. This is intentional for speed and results are unaffected. `setUnusedToOne()` exists for callers who need clean FP flags.
- "True" complex division computes `1/divisor` and then multiplies. This is faster but less accurate (about 1.5 ulp) and range-restricted.
- `_mm256_blendv_ps` is avoided because GCC 12 can expand it into a branch per element.
- `min_ps`/`max_ps` return their second operand on a tie or NaN, so the min/max kernels pass `in2` first (and `zneg`/`zpos` pass 0 first) to match `std::min(in1, in2)` in the default versions. The `minMax` reduction passes the loaded value first so that a NaN element is skipped.
- `multSum` and `multcSum` results can differ in the last bit between dispatch paths: the AVX-512 and AVX2 versions use FMA (one rounding), the AVX and default versions round the product first. Built with `-march=native`, GCC can fuse the AVX version too.
- The int8/int16 to float conversions run from the end of the buffer to the start, so the in-place `void*` wrappers work even though the output is wider than the input. Their AVX512 versions also require AVX512BW and AVX512VL, for masked byte/word loads and 512-bit byte/word min/max (the min/max loops cover 64 or 32 elements per pass): the target is `"avx512f,avx512bw,avx512vl"`, since g++ 12 rejects `"avx512bw"` on its own in a dispatched target. AVX and AVX2 have no masked byte/word loads, so their versions do the partial register first, by loading the last full register (overlapping the one before) and storing only its last `rem` floats with `rmasks[rem]`, and convert buffers shorter than one register one element at a time. Their AVX2 min/max versions also find the min/max on the raw bytes/words (256-bit, 32 or 16 elements per pass); each remainder register is loaded for the min/max with a broadcast that repeats its 8 integers across the register, and the main pass loads and converts every register before storing any of them, which is 10-17% faster with icpx than alternating. The scalar int16 loops read the input with `memcpy`: in place, the `int16_t` input and `float` output alias, and otherwise icpx assumes they don't and reorders the loop.
- `multe`, `dive`, `divre` and `divnre` run from the end of the buffer to the start, so they work in place with the complex output over in1 or in2, and their SIMD versions store only the real parts (AVX-512 mask `0x5555`, AVX/AVX2 `maskstore` of every other float), so the imaginary parts are never written. On TGL the masked stores were also faster than loading the output and blending the products in.
- `cnvrtInt32ToFloat` without min/max, `remult`, `immult` and the inversion functions without Newton-Raphson (`inv`, `invr`, `invs`, `invrs`, `invSqrt`, `invrSqrt`, `invSqrts`, `invrSqrts`) have no AVX2 version: their AVX versions already use only the instructions an AVX2 one would. `dive` and `divSqrt` have none either: the divider limits them, so AVX2's permutes gained little over AVX's unpack and permute2f128 (on TGL, `dive` 0.62 vs 0.63 cycles per element, `divSqrt` 1.37 vs 1.39-1.41). The polar/cartesian AVX2 versions are the AVX ones recompiled (plus FMA in the `cartToPol` magnitude), because SVML's AVX2 `sincos` is about 2.4x and its `atan2` 1.2-1.4x faster than its AVX ones.
- On the SVML path, `cartToPol`/`cartToPolRad` set re to ±1 wherever `re|im` compares equal to 0 (the bits of 1.0 or'd into re) before the `atan2`, which gives the same result, and their default versions move re away from 0 by ±1 wherever im is 0 (branch-free, since the angle only depends on re's sign there), since icpx vectorizes those loops with SVML. SVML's AVX-512 `atan2` takes a slow path for any register with a (0,0) input (1.8x slower with one per 37 elements, 5.3x on zero-padded data), and every SVML `atan2` returns NaN for a both-denormal pair when denormals are treated as zero (DAZ, icpx's default). The float compare, rather than a bit test, is what also catches the denormal pairs under DAZ. Without DAZ, both-denormal inputs still hit SVML's slow path; they are left alone, since their angle is real. `evm_trig.h`'s `atan2` has neither problem.
- `evm_trig.h` uses the Cephes single precision polynomials. `sincosCyc` reduces the phase exactly (to the nearest quarter cycle), so `polToCart` keeps full accuracy at any phase, unlike SVML or `sincosf(2*pi*ph)`; the default `polToCart` removes whole cycles before `sincosf` for the same reason. Its AVX2/AVX versions give NaN past |ph| = 8.5e37, where `4*ph` overflows (removing whole cycles first would cost 13-20%); the AVX-512 one rounds with `roundscale` and has no limit. `sincosRad` reduces with pi/2 in three pieces with FMA (five 8-bit pieces on AVX) and is accurate to |x| = 65536, beyond which those lanes fall back to scalar `sincosf`. Accuracy is about 1.7 ulp for sin/cos (3.3 for radians on AVX) and 2.5 ulp for `atan2`, against 0.6-0.9 for SVML, which is why the radians and `atan2` functions keep SVML when it is available. `evm_trig.h`'s `atan2` needs no NaN pass-through: it does one division, and a NaN input always reaches its numerator or denominator. For both-infinite inputs the denominator stays |x| = INF rather than being set to 1, which still gives the pi/4 base (0/INF = 0) and makes a NaN x with an infinite y give 0/NaN. A final NaN check cost 8% with icpx on AVX-512, 9-13% on AVX2 and 12% on AVX (g++ 4-5%).
- `multDivnr`, `divnre` and `divnrg` apply their Newton-Raphson stage to the quotient on the AVX-512 and AVX2 paths (for `multDivnr`, `q0 + r*(in2 - in3*q0)` with `q0 = in2*r`), rather than to the reciprocal as the `divnr` kernels do. With FMA it costs the same and is more accurate: on AVX-512 it equals the true divide 99.8% of the time (`divnr`'s reciprocal form about 82%). The AVX versions have no FMA, so they refine the reciprocal like `divnr`.
- `divg`, `divrg` and `divnrg` run front to back, which works in place since output k comes from input k*stride >= k. They don't use the gather instructions. With the Gather Data Sampling microcode mitigation (Intel Skylake through Ice Lake/Tiger Lake/Rocket Lake), each gather, ymm or zmm, takes about 28 cycles, which made them 2.2x (AVX-512) and 4x (AVX2) slower than scalar loads on TGL. Instead, the shared helpers `stridedLoad512`, `stridedLoadAvx2` and `stridedLoadAvx` (defined just before them) take small strides out of whole registers with permutes: AVX-512 uses a chain of `vpermt2ps` up to `STRIDED_PERM_MAX` = 8 (indices from `stridedIdx512`, set once per call; each step only sets its own register's lanes, so a `switch` with fallthrough runs them, which is 25% faster at strides 3-4 than a loop, where g++ tests the stride after every step), AVX2 uses fixed shuffles for strides 2-4, and AVX for stride 2. Other strides load each float and insert it (`_mm256_setr_ps`). At strides 2-4 this runs at the divider's speed on AVX-512 (0.64 cycles per output, 7x faster than the gathers). The main loop only takes registers whose whole input span (16 or 8 times the stride) lies inside the buffers. The last 1-16 (or 1-8) outputs use masked loads, or in the insert case lanes that repeat the last float, so nothing past the end is read. With buffers that aren't 64-byte aligned and come from L2, the permutes at strides 6-8 are up to 30% slower than inserts, since every register load then spans two cache lines (aligned, they're 25-45% faster). A stride <= 0 is a no-op in every version, including the defaults (where a stride of 0 would never end).
- `divSqrt` computes the square root and then its reciprocal with one divide, and multiplies by that, like the complex/real `div` (see "true" complex division above). `divnrSqrt` refines `rsqrt` with `r + 0.5*r*(1 - x*r*r)` on the FMA paths, which is more accurate than `0.5*r*(3 - x*r*r)` (on AVX-512, 1 ulp of 1/sqrt vs 2, and correctly rounded 87% of the time vs 75%). The AVX version uses the latter. The eps overloads, and `divSqrt`, `divrSqrt` and `divnrSqrt`, clamp the divisor with `max_ps(eps, x)` (x second, see min/max above) to match `std::max(x, eps)`.
- `dotpRev` and `dotpcRev` read in2 from the end. Their complex kernels are the same apart from the final sum (`dotp`'s `addsub` against `dotpc`'s negated term). Each full register of in2 is reversed with one permute (AVX-512/AVX2 `vpermps` or `vpermpd`); for real*complex, the permute that duplicates the reals reverses them instead, which costs nothing extra. The last `rem` elements of in1 line up with the first `rem` of in2, which are loaded masked and reversed with the reversing index shifted down by the register width minus `rem`. Permutes use only the low index bits, so the negative indices wrap around onto the zeroed lanes. AVX has no variable permute across the 128-bit halves. Its complex 2-register loops therefore blend the halves of the two in1 registers into [0,1|6,7] and [4,5|2,3], and read in2 in the matching order: [7,6|1,0] from two 128-bit loads and [3,2|5,4] from one load (numbering the block's elements of in2 from its start). The real*real `dotpRev` does the same with 4 floats per half: in1 [0-3|12-15] and [8-11|4-7] with in2 [15-12|3-0] and [7-4|11-8]. The obvious half swap of a loaded register is slower with icpx. It turns every form of it (insertf128 of adjacent 128-bit loads, `permute2f128(x, x, 1)`, broadcasts plus a blend) into a `vperm2f128` from memory whose unused first source is any register it picks. In the loop that was an accumulator, so each iteration waited for the last one, 3x slower. The 1-register block runs before the loop for the same reason, and the AVX complex and real*real tails build their reversed registers from 128-bit pieces. The real*real AVX-512/AVX2 `dotpRev` passes its reversing index through an empty `asm` statement, which hides it from the optimizer. With the constant index, icpx turns the `vpermps` into a `vpermilps` plus a `vshuff64x2` (AVX2: `vpermpd`), 2 shuffles per register instead of 1, which made it 1.8-2.1x slower at 1024 elements. g++ keeps the `vpermps` either way. With aligned buffers, the in2 loads straddle cache lines whenever `len` isn't a multiple of the register width, so short calls take about 1-2.5 ns longer than `dotpc`.
- The normalized dot-products split 2 registers of each input into a register of real parts and one of imaginary parts (`shuffle_ps` 0x88/0xdd, the same lane order for both inputs), so the product, its squared magnitude and its scale are computed once per element rather than once per float. In every version, defaults included, a product whose squared magnitude is below FLT_MIN (a magnitude below about 1e-19) adds nothing. AVX-512 zero-masks `rsqrt14`/`div` with a compare; the others `and` the scale with one. The guard has three jobs. An exact zero would otherwise give 0*inf = NaN. The zeroed lanes of the last registers need it anyway. And AVX/AVX2 `rsqrt` returns inf for a denormal input (AVX-512 `rsqrt14` doesn't), so a lower threshold would make the paths disagree. The `r` versions have no Newton-Raphson step. On TGL with icpx, at 1024 elements, one would cost about 40% (AVX-512 163 to 226 ns, AVX2 187 to 266 ns, against 355 and 348 for the true versions; on AVX a refined version is as slow as the true one) to bring the error from 2e-6 (AVX-512) or 1e-5 (AVX2/AVX) of the number of terms on random data down to the true versions' 1e-8. When all products have the same phase, the errors are 1e-5 against 9e-7. A product above about 1.8e19, whose squared magnitude overflows, also adds nothing, except in icpx's fast-math vectorization of the default versions, which gives NaN.
- The Newton-Raphson inversions (`invnr`, `invnrs`, `invnrSqrt`, `invnrSqrts`) refine 1/x with `r + r*(1-x*r)`, as `fmadd(r, fnmadd(x, r, 1), r)` on AVX-512, not with `divnr`'s `r*(2-x*r)`. At the same cost it is more accurate: 0.53 ulp and 99.7% correctly rounded on AVX-512, against 1.48 ulp and 77%. The square roots use `r + 0.5*r*(1-x*r*r)`. Unlike `divnr`, they keep the true results for zero and infinite inputs. There, the error term (`x*r-1`, or `1-x*r*r`) is NaN (0*INF), and r is already the INF or 0 the true result is. AVX-512 keeps r in those lanes with a compare into a mask and `mask3_fmadd`, which is nearly free. AVX2/AVX clamp the error term instead, one op that keeps the FMA: `max(x*r-1, -1)` turns the NaN into -1, so `r - r*(x*r-1)` gives 2r, and `min(1-x*r*r, 1)` turns it into 1, so the refinement gives 1.5r. Both are still the INF or signed 0 of the true result (`max_ps`/`min_ps` return their second operand for a NaN, and the error term is never past the clamp otherwise). The form `r - r*(x*r-1)`, not `r + r*(1-x*r)`, also keeps the -0 of 1/-INF. Masking the correction instead took 3 ops: on AVX2 `invnr` took 85 ns at 1024 floats against 68 with the clamp (53 unguarded, `inv` 157), and `invnrSqrt` 134 against 113. Without DAZ, the AVX2/AVX versions give NaN for a denormal input, where `rcp_ps`/`rsqrt_ps` alone give INF (see below). The scaled ones multiply the refined value by scale instead of refining scale*r (as `multDivnr` does), since that gives the wrong sign of zero for a zero scale. This costs about 0.5 ulp (`invnrs` 1.2 ulp on AVX-512). On AVX-512, `invnrSqrt` (1.03 ulp) is more accurate than `invSqrt`'s square root and divide (1.48 ulp).
- Without DAZ, AVX/AVX2 `rcp_ps`/`rsqrt_ps` treat a denormal input as zero (INF where AVX-512 `rcp14`/`rsqrt14` and the defaults give a finite value), and `rcp_ps` gives 0 instead of a denormal for |x| above about 8.5e37. This applies to every reciprocal-approximation kernel (`divr`, `divrSqrt`, `magr`, `magSqDivr`, the inversions; the Newton-Raphson inversions give NaN there instead of INF). With FTZ/DAZ (icpx's default, `enableFastDenormals()`) all paths agree. `invrs`/`invnrs` (like `divr`, and `magSqDivr` for its divisor) give 0 for |in| above 8.5e37 on every SIMD path under FTZ, since 1/in underflows before the scale is applied.
- The complex-input magnitude functions with a real output (`magSq`, `mag`, `magr`, `magSum`, `magrSum`, `magBias`, `magrBias`, `magSqSum`, `magSqMult`, `magSqMults`, `magSqDiv`, `magSqDivr`, `magSqDiff`) split 2 registers into real and imaginary parts that are already in element order, with two `permutex2var` on AVX-512, rather than two `shuffle_ps` and then a `permutexvar` on the result. That is one shuffle less (with icpx at 1024 elements, `magSq` 11% faster, the others 2-5%, and no change for `mag`, which the square root limits), and a second real input or the output buffer needs no reordering. g++ loads each input register twice for the two permutes (`vpermt2ps` overwrites its first source, and g++ reloads it rather than copying it), so with g++ `magSq` is 4% faster at 1024 elements but 4% slower in L2, and `magr` the same at 1024 and 4-6% slower in L2 (with icpx it is 5% faster at 1024 and 3% in L2). AVX2 keeps the `shuffle_ps` pair and one `permutevar8x32`; AVX regroups the halves with two `permute2f128` first. These kernels run at about 3 cycles per 16 outputs on AVX-512, not the 2 the port counts give: with complex input and real output the loads advance twice as fast as the stores, so some loads always meet a store at the same offset within a 4 KB page, wherever the buffers are. Only the functions the divider doesn't limit have an AVX2 version (`magrSum`, `magrBias`, `magSqSum`, `magSqDiff` and the complex `magSqMult`, `magSqMults` and `magSqDivr`: 16-31% faster than their AVX versions with icpx), plus `nmagnr`, whose refinement uses FMA (12% faster). `nmag`, `nmagr`, `magSum`, `magBias` and the complex `magSqDiv` gained 0-6%, and the real-input overloads use nothing AVX2 adds.
- On AVX-512, `magrSum` and `magrBias` compute |in| from m = |in|^2 and `rsqrt14(m)` so that a zero gives 0 and an overflowing |in|^2 gives INF, as the true versions and AVX/AVX2's `rcp(rsqrt(m))` do. `magrSum` keeps m wherever `m*rsqrt14(m)` is NaN (m = 0 or INF) with a masked move. `magrBias` instead sets r = 1 wherever m is not between 0 and INF (two compares and a merge-masked `rsqrt14` over a register of ones) and computes `m*r + bias` with one FMA. Its loop is bound by port 0, the only one with 512-bit multiplies on client cores, and the masked move can take a slot there (it made `magrBias` 19% slower at 1024 elements, the new form costs 5%), while compares only use port 5. `magrSum` has spare port 0 slots, so the move costs nothing there. `magr`'s AVX-512 version only zero-masks the `rsqrt14` (free) and gives NaN for an overflowing |in|^2, which the other paths give as INF: guarding it cost 4% with icpx (and 2.5%, 5% in L2, with g++), so it was left out for speed. Its test allows that NaN on the AVX-512 path.
- `nmag`, `nmagr` and `nmagnr` use the normalized dot-products' layout and guard: an element whose squared magnitude is below FLT_MIN gives 0 in every version, defaults included. One whose squared magnitude overflows gives 0 too, since its scale is 1/INF (icpx's fast-math default versions give NaN there). The scaled parts are interleaved again with `unpacklo`, which gives the first register's elements, and `unpackhi`, which gives the second's, so no cross-lane permute is needed and the AVX versions use the same shape. `nmagnr` refines `rsqrt` with `r + 0.5*r*(1-m*r*r)`. Where m overflows, r is 0 and the correction would be INF*0 = NaN. AVX-512 keeps r there with a compare and `mask3_fmadd`, as `invnrSqrt` does (2% at 1024 elements); AVX2/AVX compute the correction from min(m, FLT_MAX), which makes it 0, since masking it made AVX2 24% slower and the `min` costs 8%. It is the only magnitude function with a Newton-Raphson version. With icpx at 1024 elements it is 2.1x faster than `nmag` on AVX-512 (168 against 356 ns), 1.36x on AVX2 and 1.16x on AVX, at 2.3 ulp on AVX-512 (`nmag` 2.5) and 4-4.3 ulp on AVX2/AVX. For the others it would gain at most 1.2-1.7x on AVX-512 and little or nothing on AVX2 (`mag` 190 to 187 ns, `magSum` and `magBias` slower), since they do one square root or divide per element, not two, and on AVX2 the guards for 0 and INF cost about as much as the divider saves.
- AVX/AVX2 `magr` computes `|in|` as `rcp(rsqrt(|in|^2))`, not `|in|^2*rsqrt(|in|^2)`. It costs the same, but it gives 0 at zero instead of `0*inf = NaN`. AVX512 uses a zero-masked `rsqrt14` instead, because `rcp14` is 3 uops on a zmm register.
- getOptLevel SSE variants are intentional even though there are no
  SSE-optimized function

**icpx compatibility constraints** (see "Compiler-dependent notes" in the header):
- `default` variants must not use the `std::complex<float>(re, im)` constructor, `conj()`, or float-times-complex arithmetic, because icpx leaves them as undefined references inside target-versioned functions. Expand with `.real()`/`.imag()` or copy a constexpr complex and set its parts.
- `std::string` can't be constructed inside multiversioned functions. This is why `getOptLevel()` wraps `getOptLevelRaw()`.
- Multiversioned functions can't have default arguments. icpx doesn't apply a default argument from the declaration to the target versions, so a call that leaves it out fails to compile (g++ accepts it). Use a plain overload without the argument, declared next to the full one and defined after its `default` version (`divSqrt`, `divrSqrt` and `divnrSqrt` without `eps`).

**Namespace hygiene.** Keep `using std::complex` and other `using` declarations inside `namespace EVM`, never at global scope (commit f6c7ce4), so they don't leak into users of `evm.h`.

**Memory.** `aligned_allocator.h` gives STL-compatible aligned allocation. Alignment and pad are specified in bytes. `ALIGNED_VECTOR(T)` uses `evm_align`, which the `DISABLE_*` macros select: 64-byte alignment plus 2 registers of trailing pad when AVX512 is enabled. `EVM::getSize<T>(n)` rounds a length up to a whole number of registers. `EVM::enableFastDenormals()` should be called at program start.

**Processing scenarios** evm.h normally runs on longer buffers and on AVX2 or AVX-512 CPUs. When an optimization trades a few percent at short lengths (under ~32 elements) or on the AVX-only path for a long-buffer gain, the user prefers the simpler code that wins on long buffers.  Also prioritize absolute speed over FE_INVALID/FE_DIVBYZERO-clean tails.  Weight long-buffer AVX2/AVX-512 results most when recommending kernel changes; mention short-length or AVX-only regressions and let the user decide if they are worth fixing.  The exception is
dot-product methods which will normally be run on shorter buffers.

**Performance benchmark pitfalls**
- 4K aliasing: separate large std::vectors land at the same offset within a 4 KB page, so back-to-back calls serialize (next call's loads wait on the previous call's stores) and longer-latency kernels look slower at 8–64 elements. Time both that layout and buffers offset ~1 KB apart in one pool.
- Code placement: differences under ~0.3 ns per call (about 1 cycle) can come from where code lands; identical machine code measured 3.24 vs 3.46 ns in two builds. Compare versions in the same binary, best of 3+, and don't attribute such gaps to source changes without checking the disassembly.
- Extracted test copies need their `default` version too, or GCC compiles them as plain functions called directly (no ifunc dispatch), which flatters short-call timings


## Other headers

These predate evm.h and are not exercised by the current tests:
- `genfilter.h` (namespace `GenFilter`): windowed-sinc FIR design.
- `polyphase.h`: polyphase filter bank from such filters.
- `resampler.h` / `resamplerps.h`: arbitrary-rate resampling. Both define `class Resampler`, so never include both in one translation unit. They still refer to old `-DHAVE_SSE*` / `HAVE_CONFIG_H` macros and an `inc/config.h` that doesn't exist.
- `constel.h` (namespace `Constel`): PSK/QAM constellations and bit mapping.
- `timecode.h`: sample-indexed timestamps.
- `equalizer.h` (LMS) and `dft_wrapper.h`: depend on Intel MKL (`mkl.h`).

`dft_wrapper.h` is a non-compiling stub, and `unit_test/constel_test.cc` is unfinished and does not compile.
